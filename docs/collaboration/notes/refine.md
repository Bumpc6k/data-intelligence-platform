# 知识提炼流水线（M3-05 / Issue #16）

一句话：**解析 → LLM 初筛 → 规则校验 → 报告**。跑完你得到一份报告，**候选池一个字都不会变**。

```bash
# 在仓库根跑（WSL）
PYTHONPATH=packages/dip-refine/src:packages/dip-contracts/src:packages/dip-core/src:integrations/lineage-client/src \
.venv/bin/python -m dip_refine \
  --project /root/projects/sql-lineage-mvp/examples/warehouse \
  --project-root /root/projects/sql-lineage-mvp \
  --model deepseek-v4-flash \
  --out docs/evidence/refine --stem refine-report
```

产出两份同内容的报告：`refine-report.md`（给人看）+ `refine-report.json`（留档/下一步用）。
先小步试跑用 `--limit 3`（一次脚本一次模型调用，**有配额成本**）。

## 1. 四步各做什么

| 步骤 | 干什么 | 关键设计 |
| --- | --- | --- |
| 解析 | 走内核 `/parse` 拿脚本结构（表 / 字段 / 语句 / 列血缘） | **只按接口调用**（冻结资产）；用 `/parse` 而不是 `/analyze`，因为后者会往内核落盘 HTML 报告 |
| 初筛 | 把结构 + 白名单喂给模型，要它给「值得留下的口径」的 JSON | 只经**平台模型网关**（`/v1/chat/completions`），换模型只改配置；温度固定 0（可复现） |
| 规则校验 | (a) 契约校验（复用 `validate_draft`）(b) 事实校验（复用 `guards.check_answer`） | 与 #12 的提交接口**同一套规则**，避免"流水线自己定一套格式" |
| 报告 | 每条候选：出处 + 公式 + 依赖 + 置信度 + 模型理由 + 校验结论 | 不完整时**顶部明写"本报告不完整，别据此入库"** |

**来源不听模型的**：候选的 `source_script` 与 `source_line`（语句序号）由流水线按解析结果填。
模型自己写的来源路径一律忽略（试过，它会编）。

## 2. 白名单有四份，别混

| 集合 | 用途 | 为什么单独一份 |
| --- | --- | --- |
| `tables` / `fields` | 精确核对 `subject` 与 `depends_on`（**要入库的字段**） | 只认真实表与真实字段 |
| `numbers` | 核对自由文本里的数字 | SQL 里本来就有的 `NULLIF(x, 0)` 的 `0` 不算编造 |
| `quote_ok` | 核对**模型理由**里引用的标识符 | 模型复述 SQL 会写成 `s.sale_qty` 这种"别名.字段"，那不是编造；凭空造 `x.y` 才算 |

## 3. 报告怎么读

- **第 2 节**：通过校验的候选 —— 仍然要人抽检，校验只说明"格式齐、表字段没编"。
- **第 3 节**：有问题的候选 —— 逐条给出是契约问题（缺来源/格式非法）还是编造（表/字段/数字）。
- **第 4 节**：人工抽检建议 —— 置信度**最低**几条 + **最高**几条 + 随机几条（固定种子，报告可复现）。
- **第 5 节**：失败与错误 —— 有它就意味着报告不完整。

抽检记录用 `templates/人工抽检记录.md`，**判"不确定"按不合格处理**（不确定就不许入库）。

## 4. 为什么只出报告不落库（Issue 的边界）

- 提炼是**机器猜**出来的：模型给的公式对不对，只有懂业务的人能判。自动入库等于让模型定口径。
- 于是一条口径进知识库要过两关：**机器把关格式与事实**（本流水线）→ **人把关业务**（抽检）→
  才用它熟悉的通道提交：`POST /api/knowledge/candidates`（`submitted_by` 填真人，
  不许用流水线的标记 `提炼流水线（未入库，待人工抽检）`）。
- 证据里有一条硬核对：跑前跑后 `knowledge_candidates` / `knowledge_metrics` 行数**一字未变**。

## 5. 踩过的坑（写下来免得再踩）

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 数字白名单为空 | 模型复述 SQL 里的 `NULLIF(x, 0)` → 被判「编造数字 0」，**假红** | 数字白名单从脚本字面量收（`NUMBER_RE` + `normalize_number`） |
| 只给真实表名 | 模型复述 `s.output_qty - s.sale_qty` → 被判「编造表名」，一次误伤 11 条候选 | 自由文本用 `quote_ok`（真实表名 ∪ 脚本里出现过的 `别名.字段`） |
| 用 `/analyze` 解析 | 会顺带往内核落盘 HTML 报告，跑一个项目就是几十份 | 用 `/parse`（纯解析，不落报告、不查口径） |
| `--project-root` 没设对 | 报告里的来源路径与内核 `source_file` 对不上，将来无法互相指认 | 把 `--project-root` 指到仓库根（内核的 `source_file` 就是相对仓库根的） |
| 模型返回带代码围栏 | `json.loads` 直接炸 | 先剥 ``` 围栏再解析；**解析不了就是失败**，不用正则抠字段 |
| 模块级引用依赖 | 测试注入的假实现被绕过（`_gather_conflicts` 那个坑的同类） | 依赖一律作为参数传进来 |

## 6. 当前不做的事（别指望它）

- **不做等价判断**：`A+B` 与 `B+A` 视为不同公式；不去猜模型的公式对不对。
- **不批量并发**：一条语句一次调用，顺序跑（先要可读、可复现的报告）。
- **不做全量初始化**（Issue 边界）：一次一个项目，报告给人看，不入库。
- **不做术语/规则两类提炼**：本轮只提炼口径（`kind=metric`），另外两类通道还没有。

## 7. 谁负责

- **抽检必须是人**：`templates/人工抽检记录.md` 的四项勾全，才允许提交候选。
- 代码与测试：AI 起草（Hermes Agent），提交人逐行复核后合并。
