# 双人分工 与 Windows 端数据开发约定

> 2026-09-26 ｜ 场景：**2 名开发者**（你：Windows 端做数据开发为主；朋友：代码开发为主）+ 各自的 AI 助手
> 配套：[`2026-09-26-开发规范与AI协作.md`](2026-09-26-开发规范与AI协作.md)（通用规则）、[`AGENTS.md`](../../AGENTS.md)（AI 须知）

本文只讲两件通用规范没覆盖的事：**① 分工与交接点 ② Windows 端数据开发的特殊约定**。

---

## 1. 分工（按"谁能做决定"划，不按"谁写得多"划）

| 面 | 你（数据开发 + 产品判断） | 朋友（代码开发） |
| --- | --- | --- |
| **业务口径** | ✅ **唯一责任人**：口径对不对、公式怎么算、哪些表算核心 | 不判断业务对错，只按 Issue 实现 |
| **数据侧** | ✅ SQL 脚本、demo 数据、表结构、字段中文名 | 提供工具支持（解析、校验、入库流水线） |
| **平台代码** | 可参与（尤其前端与验收） | ✅ 主力：skill / 防火墙 / 网关 / 前端 |
| **原型与交互** | ✅ 提需求、看原型、拍板（我出原型） | 按定稿原型实现 |
| **验收** | ✅ 业务验收（"答得对不对"） | 技术自检（门禁 + 测试） |
| **架构决策** | ✅ 拍板（ADR 由我起草） | 提方案、反对要写理由 |

**交接点（只有三个，别多）**：

| 交接物 | 谁给谁 | 形式 | 触发时机 |
| --- | --- | --- | --- |
| **数据/口径样例** | 你 → 对方 | 一份可解析的 SQL + 期望的口径描述（放 `examples/`） | 对方要开发"提炼流水线/口径校验"前 |
| **接口与字段定义** | 对方 → 你 | Issue 或 ADR 里的接口草案（半页） | 动到数据结构/接口前，**先定再写** |
| **验收结论** | 我（代跑）→ 双方 | 逐条"通过/不通过 + 证据" | 每个 PR |

> 一句话：**你管"对不对"，他管"能不能跑"，我管"验没验"。**

## 2. 环境分工（避免两个人在同一台机器上互相踩）

| 位置 | 谁用 | 跑什么 |
| --- | --- | --- |
| **Windows 侧** | 你 | SQL 客户端、数据开发工具、Excel/帆软这类；**不要**在 Windows 上跑平台服务 |
| **WSL（Ubuntu）** | 朋友 + 我 | 平台服务（`:18100`）、内核（`:18080`）、审计库（`:15432`）、门禁、测试 |
| **远端** | 双方 | GitHub：Issues / PR / 门禁 CI 是**唯一事实来源** |

规则：
- **不在 Windows 上建第二套开发环境**（路径分隔符、venv 布局、编码都会带来假问题）——要跑服务就在 WSL 里跑。
- Windows 与 WSL 之间传文件用 `/mnt/c/...`（不要复制来复制去，容易两版不一致）。
- 服务起法（WSL 里，三条命令）：见 `AGENTS.md` §4；`bash ops/start-portal.sh` 会顺带带起内核。

## 3. Windows 端做数据开发的五条约定

### 3.1 红线（没有例外）

- **不许把公司生产数据带到个人环境**（导出文件、截图、样本数据都不行）。平台开发一律用**自造的 demo 数据**。
- 演示数据放仓库的 `examples/`（内核仓库已有 `examples/warehouse`、`examples/knowledge_demo`），**不要放个人目录**。

### 3.2 SQL 脚本规范（直接影响血缘解析与口径提炼）

| 规则 | 原因 |
| --- | --- |
| 文件名 `t_<表名>.sql`，一个脚本一张目标表 | 解析器按"目标表"建血缘；一个脚本多目标会让归属混乱 |
| **脚本头部注释写清业务含义**（这张表是什么、关键字段的口径） | **注释就是口径的原材料**，提炼流水线会读它；注释写得好，口径就是自动来的 |
| 只用常规语法（`INSERT OVERWRITE` / `SELECT` / `JOIN` / `GROUP BY`），**不写方言扩展与动态拼接** | 血缘解析器认常规语法；动态 SQL 会让血缘断链 |
| 字段**必须带中文名登记**（走知识库的字段词表） | 用户提问用中文（"产量"），靠中文名把问题和字段对上 |
| 分区条件写在 `PARTITION (...)` 里，不要拼进 `WHERE` | 解析器能识别分区过滤，便于影响面分析 |

### 3.3 口径回写流程（**改了必须走这条路**）

```
你在 Windows 侧发现/修订口径
  → 提交"候选"（不是直接改知识库）
  → 必须带：来源脚本路径 + 公式 + 依赖字段
  → 责任人（你）审核
  → 版本化入库（可回滚）
```

**质量门禁**：**没有来源脚本的口径一律不许入库**；同字段两条公式冲突时**必须择一**，不允许并存。

### 3.4 数据变更如何通知对方

在对应 Issue 下留一条（不要发在群里）：

```
【数据变更】<表名> <字段>
变更：<从什么改成什么>
原因：<业务原因>
影响：<下游表 / 任务 / 口径>
证据：<脚本路径 + 期望结果>
```

对方（或我）据此判断是否需要更新 skill / 防火墙策略 / 演示数据。

### 3.5 你这边最该用的两个能力

1. **血缘解析**（内核 `:18080`）：新写完一段 SQL，先跑一次解析，看上下游对不对——比人工核对快得多。
2. **报告**：解析会顺带生成自包含 HTML 报告，可以直接发给同事看（`http://127.0.0.1:18080/report/<id>`）。

## 4. 日常节奏（两个人都在业余时间，所以尽量异步）

| 节奏 | 做什么 | 形式 |
| --- | --- | --- |
| 每天 | 各自在自己 Issue 下留一条进度（进展/计划/卡点） | Issue 评论 |
| 每周一次（15 分钟） | 对齐：本周完成、下周目标、卡点、需要决策的事 | 会 or 文字 |
| 每轮结束 | 我按 Issue 验收标准逐条跑 + 给结论 | PR 评论 + 简报 |
| 有架构问题 | **不要边写边改**：开 Issue 写半页方案，对方点头再动 | Issue |

## 5. 最容易出问题的四件事（提前说清）

| 风险 | 表现 | 约定 |
| --- | --- | --- |
| **口径分歧** | 两个人都"知道"产量怎么算，但算法不同 | 口径以**你审核入库的版本**为准；有分歧先仲裁再写代码 |
| **接口没定就并行** | 各写一套，合不上 | **契约先行**：接口先定（哪怕只写签名），再并行 |
| **两个人改同一文件** | 反复冲突、rebase 到心态崩 | 同一文件同一时间只允许一人改；开工前在 Issue 留言"我在改 X" |
| **AI 产出没验证就提** | "AI 说完成了"，实际没跑 | **证据三件套**（命令 + 输出 + 含反例的测试 + 边界声明）；我复跑不出同样结果即打回 |

## 6. 你现在要做的三步

1. **把这两个文件发给朋友**：`AGENTS.md`（AI 须知）+ 本文件（分工与数据约定）
