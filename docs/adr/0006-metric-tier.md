# ADR-0006：口径分级（`tier`）——低等级免仲裁，但**不降质量门禁**

- 状态：**已采纳**（2026-09-27，源自 Issue #38；设计取舍由助手提出，需求方复核后可调）
- 相关：工作项 #12（候选池与审核流）、#13（版本与回滚）、#14（冲突仲裁）、#38（本 ADR 的来源）
- 依据：需求方原话「以后这些口径可能是分级的，低等级的不需要仲裁。」

## 背景

#12~#14 对**所有**口径一视同仁：

- 与生效口径**公式不同** → 必须显式声明 `intent=replace` 才放行（否则 409 + 冲突清单）；
- **未决候选之间**公式不同 → 一律拦（#14 从严重的那条：`replace` 的语义是"替换已生效的口径"）。

一刀切的好处是简单、可解释、不会因为"看起来不重要"而漏掉真冲突。代价是**低风险口径也要走同一套流程**：
只影响临时分析的派生指标，也被同一套仲裁拦住，人会被流程推着走形式。

## 决策

### 1. 等级是**人的判断**，不是系统推断

- 新增字段 `tier`，取值 `p0 | p1 | p2`，**默认 `p1`**（默认从严：想免仲裁必须有人明确标 `p2`）。
- `p2`（低等级）**必须**同时给 `tier_reason`（凭什么说它低风险）与 `tier_set_by`（谁定的）。
  这两条由**契约层 + 库层**双重把关（库层 CHECK：`tier <> 'p2' OR tier_reason 非空且 tier_set_by 非空`）。
- **不做自动提级/降级**：接口不收"系统推断的等级"，也没有任何代码路径会改 `tier`。
  等级只在**提交候选**时由人写入，随入库落到口径行上；要改等级 = 重新提交一条候选（带新等级 + 依据 + 人）。
  这样"等级是人的判断"这句话才有落点，且每次改动都有留痕。

### 2. 免仲裁**只放宽冲突拦截**，一条质量门禁都不放松

`p2` 与 `p0/p1` 的差别只有一处：

| 环节 | `p0` / `p1` | `p2` |
| --- | --- | --- |
| 来源脚本、依赖字段必填 | 必填 | **必填**（一样） |
| 审核人必填、reject 必写原因、approve 必答 `worth_keeping` | 必填 | **必填**（一样） |
| 入库的库层 CHECK（无来源不许 ingested） | 拦 | **拦**（一样） |
| 与生效口径公式不同 | 必须 `intent=replace`，否则 409 | **不拦**，冲突清单仍记在候选行上 |
| 与未决候选公式不同 | 拦 | **不拦**，同样留痕 |

明确不做的那件事：**`p2` 不等于"提交即入库"**。入库是"动作"，要有责任人（`ingested_by`）与审核记录；
`p2` 免的是"先仲裁"，不是"免审核"。低等级口径仍然走 提交 → 单人审核 → 入库 这条真流程。

### 3. 等级**不版本化**

版本（`version`）描述的是**口径内容**（公式、依赖字段、来源）的演进；`tier` 是"人对这个口径当下风险的判断"，
属于运维元数据。把等级塞进版本会让"同一公式的 v1 与 v2 内容相同却因等级不同被当成两次演进"，把该简单的账算复杂。

- 等级变化不改 `version`，但**必须留痕**（候选行上的 `tier` / `tier_reason` / `tier_set_by`，以及口径行的 `tier` 快照）。
- 已有的回滚语义（#13：状态翻转）不动：回滚只影响 `status`，不碰 `tier`。

### 4. 冲突判定的分级语义

`blocking_conflicts(intent, conflicts, tier)`：

- `tier in (p0, p1)`：维持 #14 的从严（与生效冲突且未声明 replace → 拦；未决候选之间冲突 → 拦）；
- `tier == p2`：两类冲突都**降级为记录**（写进候选行的 `conflicts` jsonb，界面上照样能看到"它和谁公式不同"）。

被否掉的备选：给 `p2` 单独开一个"免审入口"接口。理由：多一条写入路径 = 多一处会绕过库层门禁的地方，
而我们的质量门禁是刻意做在**库层**的（#12）。分级不该成为新入口，只该成为**已有流程里的一个判断**。

## 后果

- 好：低风险口径不再被仲裁流程挡着；风险判断被显式化、留痕、可审计（谁在什么时候说它低风险）。
- 代价：`p2` 之间的公式分歧不会被系统拦住 —— 这正是"人的判断优先"的代价，所以**默认给 `p1`**，
  并且冲突清单一定要落盘（不能因为不拦就不记）。
- 待需求方确认的两点（写在这里，不藏着）：
  1. `p2` 是否要"提交即入库"（跳过一次人工审核）？本 ADR 的取舍是**不跳**（入库是动作，要责任人）；
  2. 等级改动的追溯粒度：本 ADR 用"重新提交候选"实现改等级，是否需要专门的"改等级"接口（带独立的操作日志）？
