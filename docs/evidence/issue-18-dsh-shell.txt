===== 5. 失败路径（三种，都是实际发生的，不是演练脚本） =====
  A. 内核挂了 + skill 也挂了 → 外壳层传输失败：
    再查一次 ads.ads_产销存月报 的上游血缘（用 mcp__lineage__lineage_analyze），并如实告诉我这次调用成没成功、失败原因是什么。
    16:04
    已完成工作
    用时 5秒
    
    这次没成功——如实说明：
    
    工具：mcp__lineage__lineage_analyze（表 ads.ads_产销存月报，depth=3）
    结果：失败。两次调用（含一次重试）都只返回 Error: fetch failed，均没有拿到回执（无 endpoint、无 evidence_count、无 HTTP 状态码）。
    失败原因：只能确定是传输层/网络层失败——请求根本没走通、没到达血缘端点，所以服务端没有返回任何响应，不是"表不存在"或"血缘图里查不到"这类业务原因（那种情况上一步会返回 found:false 或带错误信息的回执）。具体是端点宕了、连接被拒还是 DNS/代理问题，从这条报错看不出来，我不编造。
    
    因此本次无法给出上游表数量；本会话上一次成功调用（回执 evidence_count=9、ok=true）的结果仍是目前唯一有证据的结论（上游 9 张表、13 条边），但那不能替代本轮的失败结果。需要的话我可以隔一会儿再试一次，或换用 SQL 解析方式（传 sql 参数）绕开取表接口。

  B. 内核挂了但 skill 在 → **我们的失败回执照出来了**（ok=false + 精确原因）：
    这次调用失败了，但拿到了回执——失败原因来自回执本身，不是我的猜测：
    
    回执字段	值
    ok / usable	false / false
    error / message	重试 1 次后仍失败：连接失败：[Errno 111] Connection refused
    evidence_count	0（无任何证据条目）
    http_status	null（请求没到服务端）
    attempts / ms	2 / 0
    tables / lineage	[] / {}
    
    也就是说：工具内部自己重试了 1 次（共 2 次尝试），都以 连接被拒（Errno 111 Connection refused） 告终——血缘服务端没有在监听或拒绝了连接，请求从未得到 HTTP 响应，因此这次查不到任何上游表。按"无证据不出结论"的规则，本轮不能给出上游表数量；上一次成功调用的结论（9 张上游表、13 条边，evidence_count=9）仍然只是历史证据，不代表当前服务可用。等端点恢复后可以再试。
