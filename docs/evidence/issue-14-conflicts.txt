=========== 6. 反例：仲裁与冲突的四类拒绝 ===========
  缺决定    HTTP 400  missing_decision | 必须且只能指定一个落选项：keep_candidate_id（留候选）或 keep_version（留某一版）
  两个都想留 HTTP 400  missing_decision | 必须且只能指定一个落选项：keep_candidate_id（留候选）或 keep_version（留某一版）
  缺仲裁人 HTTP 400  missing_operator | 缺仲裁人：是人在做这个决定
  缺理由    HTTP 400  missing_reason | 仲裁必须写明理由（为什么留这条、为什么驳回那条）
  版本不存在 HTTP 404  version_not_found | 口径 ads.ads_产销存月报.kc124121a 没有第 99 版
  候选不存在 HTTP 404  candidate_not_found | 候选 #999999 不在 ads.ads_产销存月报.kc124121a 的未决候选里

=========== 7. 库层拦什么、接口拦什么（如实说明）===========
  库层不变量（任何写入路径都拦得住）：
    · 同一口径只能有一条 active 版本        → uq_kb_metrics_one_active
    · 无来源 / 无公式 / 无依赖不许入库      → knowledge_metrics_source_required_chk
    · 回滚必须留下谁、为什么               → knowledge_metrics_rollback_trace_chk
    · 说不清原因的拒绝不算审核             → knowledge_candidates_reject_reason_chk
  策略层（接口 + 人）：候选之间的公式冲突 —— **刻意不做库层约束**，因为判「该留哪条」是人的事
  （Issue 边界：不做自动仲裁）。所以直接写库造两条竞争候选是做得出来的，但它：
    · 不会导致两条生效版本（入库仍受库层不变量约束）；
    · 会被 GET /api/knowledge/conflicts 暴露，并可用仲裁收敛。
